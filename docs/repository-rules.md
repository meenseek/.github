# 저장소 운영 규칙

## 목적과 상태

이 문서는 `meenseek` GitHub 조직의 저장소 이름, 소유권과 사용 방식을 정하는 공개
규칙입니다. 새 저장소를 만들겠다는 계획이나 일정은 아닙니다.

- 현재 상태는 GitHub의 실제 저장소와 각 저장소의 문서·설정을 확인합니다.
- 후보는 아래 조건을 충족했을 때만 생성합니다.
- 비어 있는 저장소나 패키지를 미래 필요성만으로 미리 만들지 않습니다.
- 각 저장소의 `AGENTS.md`나 실행 가능한 정책에 더 구체적인 규칙이 있으면 그 규칙이
  우선합니다.

## 명명

- 저장소명은 제품명 또는 현재 책임을 기준으로 짧게 정하며, 조직명은 기본적으로
  생략합니다. 제품의 독립 구성요소는 `<제품명>-<역할>`로 구분합니다.

## 현재 저장소 확인

현재 공개 저장소는 [GitHub 목록](https://github.com/orgs/meenseek/repositories?type=public)에서
확인합니다. 이 문서는 목록을 복제하지 않고 저장소의 소유권과 생성 조건을 정합니다.
비공개 저장소에도 같은 기준을 적용합니다.

## 조건부 후보

공통 기반 패키지 저장소 `product-foundation`과 제품 시작 템플릿
`next-product-starter`는 아래 조건을 충족할 때만 만드는 후보입니다. 후보를 현재
존재하는 저장소나 확정된 생성 계획으로 간주하지 않습니다.

패키지 이름은 `http-client`, `next-config`처럼 제공하는 기능을 구체적으로 드러냅니다.

## 사용 방식과 소유권

### 디자인 시스템

- 제품이 배포된 패키지를 설치합니다.
- 의미 기반 토큰과 범용 UI 컴포넌트를 소유합니다.
- 제품 화면, 비즈니스 컴포넌트와 제품 도메인을 소유하지 않습니다.
- `product-foundation`이나 특정 제품에 의존하지 않습니다.

### 공통 기반 패키지

- 제품이 버전이 고정된 패키지를 설치합니다.
- 제품 도메인과 무관하고 여러 제품에서 검증한 런타임 기능만 소유합니다.
- 제품별 DB 모델, 권한 정책, 화면 흐름, 프롬프트와 평가셋을 소유하지 않습니다.
- 제품, 시작 템플릿 또는 사용처 검증 fixture를 런타임 의존성으로 참조하지 않습니다.

### 제품 시작 템플릿

- 새 저장소를 만들 때 초기 파일을 한 번 복사합니다.
- 생성된 제품은 복사된 파일과 이후 변경을 직접 소유합니다.
- 시작 템플릿의 변경은 기존 제품에 자동 전파되지 않습니다.
- 계속 동기화해야 하는 동작은 시작 템플릿에 두지 않습니다.

### 독립 제품·실험

- 코드, 도메인, 데이터, 환경, 배포와 제품 릴리스를 직접 소유합니다.
- 공통 패키지를 사용할 수 있지만 공통 기반 패키지가 제품을 역으로 참조하지 않습니다.
- 다른 제품의 요구를 대신 수용하는 공통 코드 저장소가 되지 않습니다.

## 문서 소유권

조직 저장소의 문서 배치 기준은 이 절이 소유합니다. 각 저장소는 실제 문서의 소유 범위를
로컬 `AGENTS.md`에서 연결하고, 더 구체적인 기존 계약과 적용 범위를 확인합니다.

| 위치 | 기본 책임 |
| --- | --- |
| `README.md` | 시스템의 목적·아키텍처·구성요소·데이터 흐름·소유 및 실행 경계를 독자에게 설명합니다. |
| `AGENTS.md` | 에이전트의 시작·scope 선택·실행·검증·적용·복구·정리 조건과 해당 저장소의 문서 소유권을 안내합니다. |
| `docs/*.md` | 특정 기능·도메인·설계의 판단과 저장·조회 계약을 소유합니다. 로컬 실행 지침은 `AGENTS.md`로 연결합니다. |
| `SKILL.md` | 해당 스킬의 호출 조건·입력·실행 흐름·도메인 연결을 소유합니다. 제품 계약과 공통 기준은 원래 소유 문서를 참조합니다. |
| 코드·schema·설정 | 실행 가능한 타입·입출력·저장 및 권한 계약을 소유합니다. 문서의 예시는 설명이며 독립된 구현 계약을 만들지 않습니다. |
| Git history·기존 작업 기록 | 변경 이유·검증 결과·완료 및 과거 진행 상태를 소유합니다. 상시 문서에 실행별 원장을 복제하지 않습니다. |

한 기준은 한 문서에서 수정하며 사용처는 소유 문서와 필요한 절을 참조합니다.
이동할 때는 기존 의미·승인·보존·실패 대응을 유지하고, 실제 호출자가 읽는 진입점과
링크·진단 메시지를 함께 갱신합니다. 문서 이동만으로 기능·설치·복구의 성공을 주장하지 않습니다.

이 저장소는 조직의 저장소 운영·문서 배치 기준을 소유합니다. 개인·회사 자료에 공통인
native 작업 선호·품질·접근·개인정보 규칙은 해당 native 원문 소유자에게 남깁니다.
이를 공개 Git으로 복제하거나 ontology 제품의 로컬 실행 절차를 조직 공통 정책으로 만들지 않습니다.

### 공개 문서와 비공개 운영 자료

저장소가 공개이면 현재 파일뿐 아니라 commit·PR·issue의 문구와 첨부도 공개 자료로
취급합니다. 문서의 필요성과 공개 가능성은 각각 확인합니다.

| 공개 위치에 둘 자료 | 소유자 통제 운영 위치에 둘 자료 |
| --- | --- |
| 설치·개발·기여 방법, 아키텍처와 공개 인터페이스 | 사업 목표, 가격·수익·시간·비용 가정과 중단 기준 |
| 제품 안전·개인정보 제약과 구현·검증 계약 | 채널 전략, 미게시 원고, 승인·게시·관측 기록 |
| 비밀값을 제외한 설정 예시와 실제 지원 범위 | 고객·계정 원문, 내부 분석과 공개하지 않은 자산 |

사업 계획이나 원고를 의도적으로 공개하려면 소유자가 해당 내용과 범위를 지정해
판단합니다. 민감정보·비밀값·고객 원문·native 비공개 원문과 공개 승인 없는 비공개
저장소 이름·경로는 공개 문서나 변경 설명에 넣지 않습니다.

혼합 문서는 구현·검증에 필요한 공개 계약과 비공개 운영 판단을 분리하고 각 기준의
소유자를 하나로 유지합니다. 비공개 사용처가 공개 계약을 참조할 수는 있지만 공개
문서에는 비공개 원문을 복제하거나 접근할 수 없는 링크를 진입점으로 두지 않습니다.
필요한 운영 원문에 접근하지 못하면 해당 판단을 보류하며 공개 예시로 대신하지 않습니다.

이동할 때는 적용되는 소비자·자동화의 참조, 승인 조건과 보존 자산을 함께 확인합니다.
현재 파일 정리와 이미 공개된 Git 이력의 삭제는 별도 작업이며, 이력 재작성은 기존
공유·보존·승인 경계를 따릅니다.

## 의존성 방향

```text
product ─────────> design-system package
product ─────────> product-foundation packages
starter ─────────> 배포된 패키지
consumer fixture ─> 검증 대상 foundation package

금지:
foundation production package ─X_runtime─> product / starter / fixture
design system ─X_runtime─> product foundation / product
production package ─X_runtime─> testing package
```

패키지 간 참조는 대상 패키지의 공개 export만 사용합니다. deep import나 순환 의존성을
허용하지 않습니다.

## 생성과 승격 조건

저장소를 추가하기 전에 기존 저장소의 책임 안에서 처리하거나 내부 모듈로 나눌 수
있는지 확인합니다. 분리는 독립 소유·운영의 필요성과 추가 유지 비용을 비교해
결정하며, 아래의 해당 생성·승격 조건을 함께 적용합니다.

### 공통 기반 패키지

다음을 모두 충족할 때만 제품에서 `product-foundation`으로 승격합니다.

1. 서로 독립적인 실제 제품 두 곳 이상에서 거의 같은 구현을 사용합니다.
2. 같은 요구 변경을 두 제품에 실제로 적용한 기록이 있습니다.
3. 공개 API를 제품 도메인 명사 없이 설명할 수 있습니다.
4. 차이를 작은 명시적 설정으로 설명할 수 있습니다.
5. 독립 릴리스 버전, 변경 기록, 롤백과 마이그레이션 책임을 정할 수 있습니다.
6. 독립 테스트와 실제 소비 경계의 호환성 검사를 만들 수 있습니다.
7. 추출 후의 릴리스·업그레이드 총비용이 제품별 복사본 유지비보다 낮습니다.

단순 `fetch` wrapper, 제품별 프롬프트, 공급자보다 제품 정책이 중심인 AI 코드와
범용 helper 모음은 이 조건을 충족하지 않습니다.

### 제품 시작 템플릿 생성

다음을 모두 충족할 때 생성합니다.

1. 새 프로젝트 생성이 실제로 반복됩니다.
2. 같은 초기 파일과 검증 절차가 반복됩니다.
3. 포함된 앱을 독립적으로 install, lint, test, build할 수 있습니다.
4. 장기 동기화가 필요한 런타임 로직을 포함하지 않습니다.

## 생성 완료와 재점검

이 절은 새 저장소뿐 아니라 meenseek가 유지하는 재사용 스킬·도구의 생성·설치·갱신에도
적용합니다. 기존 저장소 안에서 만들거나 operations 큐 없이 직접 작업해도 같은 기준을
읽고 적용합니다. 스킬 형식 검사는 이 완료 기준을 대신하지 않습니다.

조직 기준과 구조 검사기는 이 저장소가, 실제 연결·설정·검증은 각 저장소가 소유합니다.
operations는 필요한 실행 경로만 연결하며 모든 저장소에 큐 등록을 요구하지 않습니다.
개인 native 원문·접근·복구는 그 원문 소유자가 관리합니다. 공개 Git이나 CI로 복제하지 않습니다.

새 저장소 생성 후 첫 사용 전에 다음을 확인합니다.

1. 위 생성 조건을 충족하는 실제 목적·소유자와 독립 책임이 있는지 확인합니다.
2. 기존 README 또는 AGENTS 진입점 한 곳에 `연결과 검증` 절을 둡니다. 필요한 연결,
   적용 조건, 검증 방법과 의도적 제외의 근거를 적고 상세 내용은 원래 소유 계약을 참조합니다.
   AI 작업에 필요한 local AGENTS와 조직 기준을 실제로 읽는 진입점도 확인합니다.
   읽기 전용 보고·Issue 전용 저장소 등 소스가 필요 없는 경우에는 실제 소유 계약을 근거로
   적용 제외를 판단하며, 이름·빈 상태·archive만으로 제외하지 않습니다.
3. AGENTS.md의 검사 명령으로 실제 GitHub 상태를 대조하고, 해당 환경에서 필요한 소유자별
   읽기 전용 검증을 수행합니다. 문서나 파일의 존재를 연결 성공으로 처리하지 않습니다.
   부작용·배포·새 권한이 필요한 검증은 기존 승인 범위와 제품 계약을 따릅니다.
4. 구조 확인과 실제 연결을 각각 확인됨·실패·미확인·적용 제외로 기록합니다.
   적용 제외는 소유자의 근거가 있어야 하며 실패·미확인을 완료로 바꾸지 않습니다.
   근거에는 저장소 ID·commit, 적용한 정책·설정, 대상 환경과 실제 확인 시각을 연결합니다.

기존 저장소에 동등한 목적·연결·검증 계약이 있으면 그 소유 문서를 재사용합니다.
표준 절이 없다는 검사기의 미확인은 문서 형식의 한계이며 실제 준비 실패가 아닙니다.
실행자가 기존 계약의 의미와 필요한 연결을 확인하고, 실제 누락만 소유 위치에서 보완합니다.

생성 완료 시 대상 저장소를 검사하고 기존 조직 점검에서는 GitHub 실제 목록을 모든 페이지까지
조회해 등록 밖의 저장소도 대조합니다. 전체 접근 범위를 확인하지 못하면 목록 전체 확인은
미확인입니다. private 이름과 진단 원문을 공개 문서·커밋·로그로 옮기지 않습니다.
필요한 설치본·workspace 경로는 기존 등록이나 직접 확인한 Git remote에서만 연결합니다.
미설치 자체를 모든 저장소의 결함으로 취급하거나 경로·계정·서비스 연결을 추측하지 않습니다.

정책·설정·컨텍스트·서비스·지원 환경이 바뀌면 영향받는 검증을 다시 수행합니다.
이름 변경·이전·archive·재활성화·폐기에서도 저장소 ID와 현재 소유 계약으로 적용 대상을
재판정합니다. 같은 기준·입력·환경의 검증은 한 실행 안에서 재사용할 수 있으나 이전 성공을
현재 확인으로 쓰지 않습니다. 원문이 없어지거나 접근에 실패하면 삭제·폐기로 추정하지 않습니다.
실패·미확인은 기존 작업·제품 소유 기록에 영향, 담당, 해소 조건과 다음 확인을 남깁니다.

### 재사용 스킬과 도구의 연결

원본 소유자와 버전 관리 위치를 먼저 정합니다. 기존 소유 저장소를 재사용하고, 별도
저장소는 위 생성 조건을 충족할 때만 만듭니다. 설치 폴더 자체가 Git checkout인 경우도
허용합니다. 외부 스킬을 그대로 사용할 때는 upstream과 설치한 revision을 확인하며,
이를 meenseek의 자체 원본으로 복제하지 않습니다.

원래 소유 문서에 원본의 저장소·commit·파일 경로, 설치본과의 관계, 발견·호출 경로,
필요한 정책·사용처 연결, 갱신·복구 방법을 둡니다. 경로는 실제 설치본의 심볼릭 링크나
복사 관계를 확인해 정하며, 설치본에 Git remote가 없다는 이유만으로 원본 부재를
판정하지 않습니다. 다른 환경까지 지원한다고 주장할 때만 그 환경의 접근·설치도 검증합니다.

검토한 원본과 실제 사용되는 설치본을 대조합니다. commit 고정이나 로컬 수정이 있으면
선택 근거와 적용 범위를 확인하며, main과 다르다는 사실만으로 오류로 판정하지 않습니다.
동기화되지 않은 변경은 그 영향과 반영할 소유자를 기록합니다. 파일이나 링크의 존재,
형식 검사와 단위 테스트만으로 발견·정책 로딩·실제 사용 성공을 대신하지 않습니다.

필요한 연결이 실패하거나 미확인이면 해당 사용 경로를 준비 완료로 보고하지 않습니다.
승인된 소스 작업은 계속할 수 있으며, 원격 게시·설치본 교체·배포·반복 실행은 각각
기존 승인 범위를 따릅니다. 새 원장이나 모든 스킬의 operations 등록을 요구하지 않습니다.

### 연결 리뷰

스킬·저장소 연결 리뷰는 [작업 흐름 리뷰](../AGENTS.md#workflows)의 적용 사례입니다.
적용되는 공통 코드·문서·리뷰 기준과 함께 변경된 연결에서 다음을 대조합니다.

- 실행자가 실제로 읽는 진입점과 기준의 소유 위치가 연결되는지 확인합니다. 직접 작업과
  coordinator 경로에서 정책이 누락되거나 별도 판단 규칙으로 복제되지 않아야 합니다.
- 원본과 실제 설치본, 필요한 사용처의 연결을 확인합니다. 의도한 commit 고정·미설치·
  적용 제외와 연결 실패·미확인을 구분하고, 확인하지 못한 범위를 결함으로 단정하지 않습니다.
- 변경 위험에 맞는 대표 요청과 누락·실패 상황을 시뮬레이션해 발견·호출·정책 선택·
  완료 판정이 이어지는지 확인합니다. 반복 누락을 다루는 경우 해당 입력을 재사용합니다.
- 구조 검사, 실제 설치·호출, 결과 품질의 근거를 구분합니다. 가상 환경이나 테스트의
  성공을 실제 설치 또는 모든 제품의 성과로 확대하지 않습니다.
- 리뷰 후 적용한 원본·설정과 실제 실행 경로를 다시 대조합니다. 독립 리뷰의 통과만으로
  설치·서비스 준비를 완료 처리하지 않으며, 핵심 미확인은 담당과 해소 조건을 남깁니다.

반복 점검은 승인된 기존 실행 경로와 일정이 소유합니다. 생성 절차를 우회한 저장소는
실제로 수행한 전체 목록 대조에서 발견하며, 실행하지 않은 시각·오프라인·즉시 탐지를
보장하지 않습니다. 현재 일정과 알림은 저장소에 복제하지 않습니다.

## 환원과 폐기 조건

- 공통 패키지에 운영 중인 제품·서비스의 사용처가 없다고 확인되면 사용 중단을 알린 뒤
  제거합니다.
- 검증 fixture는 사용처로 세지 않습니다. 유지할 항목이 없으면 저장소를 archive합니다.
- 공통 패키지를 사용하는 제품이 하나뿐이고 API가 그 제품 요구에 따라 계속 변하면 제품 내부로
  환원합니다.
- 예외 설정과 escape hatch가 정상 사용보다 많아지면 추상화를 폐기하거나 책임을
  다시 나눕니다.
- 시작 템플릿에 기존 제품과 계속 동기화할 코드가 생기면 템플릿에서 제거합니다. 공통
  패키지로 옮길 때는 위 승격 조건을 적용합니다.

## 문서 갱신 규칙

- 저장소 목록과 공개 상태는 GitHub에서 확인하고 이 문서에 복제하지 않습니다.
- 소유권, 생성·승격 조건이나 사용 방식이 바뀌면 이 문서를 갱신합니다.
- 비공개 저장소 이름은 별도 공개 승인 없이 적지 않습니다.
- 현재 상태와 조건부 후보를 한 상태처럼 섞지 않습니다.
- 후보 이름을 실제 존재 증거로 사용하지 않습니다.
- 링크, 공개 패키지와 지원 범위는 실제 GitHub와 registry 상태를 확인한 뒤
  기록합니다.
